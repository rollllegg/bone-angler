# 剧情系统设计

> 依据：`SHIFT/docs/叙事与文案协作流程.md`。
> 一句话：把流程文档里的状态模型、分支树、结局、账本和正文，变成游戏能直接执行的数据；人继续只写种子、正文和规则。

## 1. 边界

剧情系统不是对话框，也不是把飞书文案抄进代码。它接住流程文档的四类产物：

| 流程产物 | 系统里的位置 | 谁维护 |
| --- | --- | --- |
| 状态模型、影响规则 | 案例数据的 `state` 与条件 | AI 推演，人确认 |
| 分支树、节点表 | 案例数据的 `nodes` | AI 生成，人看分支图 |
| 正文 | `narrative/prose/` | 人 |
| 结局、回声、账本 | `outcomes`、`endings.json` | AI 推演，人确认 |
| 文本表 | `game/data/story/text/zh.json` | 编译生成 |

三条硬要求：

1. 换内容不改代码。
2. 内容错误在构建期报出来，不在玩家面前报。
3. 派生产物能重跑；聊天记录和飞书正文都不算最终真源。

## 2. 四层结构

```text
narrative/                     作者层（人写 + AI 派生，进版本库）
  seeds/                      故事种子，人写
  derived/                    AI 生成：graph.json、分支图、结局、报告
  prose/                      正文，人写

        │  story_build（Godot headless）
        ▼

game/data/story/               数据层（编译产物）
  manifest.json
  world.json                  跨案例世界状态声明
  cases/*.json                案例图
  endings.json                整局结局
  text/zh.json                TextDB

        │  StoryDB / StoryRuntime
        ▼

game/scripts/story/            运行时
game/scripts/demo/story_panel.gd  接入层（窗口、计时、存档）
```

流程文档里的两条流水线在这里汇合：剧情线产出案例图和结局，其他文案线产出 TextDB；游戏只读编译产物。

## 3. 数据契约

### 3.1 状态

状态分三个作用域，声明后才能使用：

| 作用域 | 例子 | 生命周期 |
| --- | --- | --- |
| 案例 | `clue.photo`、`named` | 一位来客接待期间，结案后快照到 `case.<id>.*` |
| 世界 | `world.hades_rampage` | 整局 |
| 运行 | `run.day`、`run.released` | 整局，由接入层写入 |

案例文件里不写前缀的 flag 属于本案例；写 `world.`、`run.` 的按对应作用域解析。flag 必须声明类型和默认值，拼错会在构建期失败，不会静默变成 false。

### 3.2 案例图

节点只有三种出口：`next`（继续）、`choices`（玩家选择）、`outcome`（结案）。构建期强制三选一。

```json
{
  "id": "wukong",
  "entry": "arrival",
  "speakers": {
    "孙": {"name": "孙悟空", "art": "guest_front"},
    "圣": {"name": "圣地亚哥", "art": "counter"}
  },
  "state": {
    "flags": {
      "clue.photo": {"type": "int", "min": 0, "max": 1, "default": 0},
      "clue.tail": {"type": "int", "min": 0, "max": 1, "default": 0},
      "named": {"type": "bool", "default": false},
      "attitude": {"type": "int", "min": -2, "max": 2, "default": 0}
    }
  },
  "nodes": [
    {
      "id": "inspect",
      "steps": [{"speaker": "圣", "text": "wukong.inspect.prompt"}],
      "choices": [
        {
          "id": "photo",
          "text": "wukong.choice.photo",
          "if": "clue.photo == 0",
          "set": ["clue.photo = 1"],
          "next": "inspect.photo"
        },
        {
          "id": "admit",
          "text": "wukong.choice.admit",
          "next": "admit.confirm"
        }
      ]
    },
    {
      "id": "inspect.photo",
      "steps": [
        {"speaker": "圣", "text": "wukong.inspect.photo.01"},
        {"speaker": "孙", "text": "wukong.inspect.photo.02"}
      ],
      "next": "inspect"
    },
    {
      "id": "admit.confirm",
      "steps": [{"speaker": "圣", "text": "wukong.outcome.admitted"}],
      "outcome": "admitted"
    }
  ],
  "canon": ["world.hades_rampage = true"],
  "outcomes": {
    "admitted": {
      "result": "release",
      "ledger": {"who": "孙悟空", "result": "已入境", "note": "wukong.ledger.admitted"},
      "effects": ["world.wukong_admitted = true"]
    },
    "refused": {
      "result": "reject",
      "ledger": {"who": "孙悟空", "result": "未入境", "note": "wukong.ledger.refused"},
      "effects": ["world.wukong_admitted = false"]
    }
  },
  "schedule": {"day": 3, "slot": 0}
}
```

节点进入时先执行 `set`（可选的进入效果），再展示 `steps`。step 可以带 `if`，用来放条件台词；`text` 只存 key。

`choices` 的 `if` 为假时整条隐藏；需要“看得见但点不了”时用 `locked_if` + `locked_text`。构建期检查每个选择节点至少有一条无条件可选的分支，避免卡死。

### 3.3 固定 canon

`canon` 是“不管玩家怎么选都必须发生”的事，结案时无条件写入。孙悟空案例里就是“冥王一定会被闹”。

构建期做两件事：

- 检查 `canon` 里的 flag 没有在别处被改成相反值。
- 检查所有 `outcomes` 都会执行同一份 `canon`。

这样 AI 不会从种子推出“拒绝就能阻止大闹”这种与 canon 冲突的分支。

### 3.4 结局

案例结局（`outcomes`）和整局结局（`endings.json`）分开。

- 案例结局决定这位来客去哪、账本怎么写、哪些世界 flag 变化。
- 整局结局在最后一天结算，按条件和优先级选一条，共享正文 + 条件尾声。

```json
{
  "endings": [
    {
      "id": "blamed",
      "priority": 10,
      "if": "world.hades_rampage && world.wukong_admitted",
      "text": "ending.blamed",
      "epilogue": [
        {"if": "case.wukong.named", "text": "ending.blamed.named"},
        {"if": "case.wukong.attitude < 0", "text": "ending.blamed.hostile"}
      ]
    }
  ]
}
```

结案时把案例 flag 快照成 `case.<id>.*`，所以尾声能读“当时有没有叫破”“孙悟空的观感如何”，而不用为每种组合写独立结局。这就是流程文档 A6 的“共享结局 + 条件尾声”。

### 3.5 账本

账本是结局的依据，也是玩家最后能翻的东西。每个 outcome 必须给一条：

```json
{"who": "史密斯", "who_if": [{"if": "named", "who": "孙悟空"}], "result": "已入境", "note": "wukong.ledger.admitted"}
```

`who_if` 按顺序取第一条命中的名字：叫破后账本记“孙悟空”，没叫破记“史密斯”。运行时追加到 `ledger` 数组，随存档保留。账本的展示可以后做，数据先落地。

### 3.6 文本

- 图里只存 key，key 由编译器按 `<case>.<节点>.<序号>` 生成，人不用手写。
- `text/zh.json` 一行一个 key，方便 diff 和热重载。
- 缺 key 时返回 `‹key›` 并上报 `missing_key`；构建期直接失败，不把它带进包。

## 4. 条件与效果

条件是一套故意做小的表达式，够用就好：

- 标识符：`clue.photo`、`named`、`world.hades_rampage`
- 字面量：整数、`true` / `false`、字符串
- 运算：`+ - * /`、`== != > >= < <=`、`and or not`、括号
- 不支持函数调用、属性访问之外的任何东西

效果只有两种：

- 赋值：`flag = 值`、`flag += 1`
- 结案：`result` 取 `release` / `reject` / `stay`

剧情数据不能直接调用游戏函数。要放行、要扣钱，由接入层读 `result` 和 `effects` 执行，白名单固定。这样 AI 生成的内容不会变成代码。

## 5. 人怎么写

人只碰三个地方。

**种子**：沿用流程文档的格式，不填表。重点是把“长期影响、必须发生、绝不能发生”写清楚，这三项决定推演能不能跑。

**正文**：按节点分节，台词用 `说话人：内容`，旁白直接写。不用写 key。

```md
# 孙悟空

## 节点 arrival
孙：喂，小子，还不赶快放俺老s……俺过去。
圣：姓名？死因？
孙：s……史密斯。吃桃子撑死的。

## 节点 inspect
圣：照片上的人脸上可没有这么多毛啊。

## 选择 photo
对照冥籍照片

## 结局 admitted
你把这个瘟神放进了冥府……
```

speaker 用案例里声明的名字或简称；编译器按声明匹配，不靠冒号猜。飞书仍然是写作界面：用 `lark-cli docs +fetch` 拉下来，落在 `narrative/prose/`，不需要手抄。

**规则**：分支不对时改“某个选择会造成什么”，AI 重新推演，人不维护组合表。

## 6. 编译与校验

`game/tools/story_build.gd`，用 headless Godot 跑，输入 `narrative/derived/<case>.graph.json` 和 `narrative/prose/<case>.md`，输出 `game/data/story/`。

构建期必须拦住：

- 引用了未声明的 flag，或类型对不上
- 条件语法错误
- 节点缺出口，或同时有两种出口
- 从 `entry` 走不到的节点
- 选择节点没有无条件可选项
- `text` key 缺失，或正文里有没被引用的段落
- outcome 缺账本，或 canon 被条件分支绕过
- step 的 `speaker` 没有声明

失败时打印文件和节点 id，退出码非 0；成功时写 `narrative/derived/story_build_report.md`。

## 7. 模拟与报告

`game/tools/story_sim.gd`，和运行时共用同一套 `StoryRuntime` 和条件求值器，避免两套实现走偏。

它做流程文档 A3–A7 的机械部分：

- 枚举每个案例的所有选择路径，按结局、案例状态、世界状态生成签名。
- 签名相同的路径合并，统计每种结果有多少条路。
- 对每个选择做“翻转测试”：翻转后签名变不变，产出 A5 的重要性矩阵。
- 多案例时做组合（可按 N 剪枝或抽样），检查整局结局可达。
- 输出：`combinations.csv`、`branch_map.md`、`endings.md`、`importance.md`、`consistency_report.md`、`content_plan.md`。

`content_plan.md` 按节点统计字数，给出“哪些必须人写、哪些可以共用、总共多少字”，直接对应 A7 的内容预算。

人只看分支图、重要性矩阵和写作清单；CSV 是给程序和模拟器的。

## 8. Godot 接入

新增：

```text
game/scripts/story/story_db.gd        载入 manifest / 案例 / 文本
game/scripts/story/story_state.gd     flag、作用域、快照、序列化
game/scripts/story/story_expr.gd      条件与效果求值
game/scripts/story/story_runtime.gd   单案例推进、选择、结局
game/scripts/story/story_text.gd      key 查询与缺 key 上报
game/scripts/demo/story_panel.gd      对话与选项面板
```

`StoryRuntime` 不认识钓鱼、药剂和金币，只暴露：

```gdscript
start(case_id, context)
current_step() -> Dictionary
visible_choices() -> Array
advance() -> bool
choose(choice_id) -> bool
is_closed() -> bool
snapshot() -> Dictionary
```

信号：`changed`、`case_closed(outcome_id)`、`text_missing(key)`。

接入点：

- `playtest_session.gd`：灵魂字典加 `story_case`；`souls` 里带 `story_state`；新增 `world`、`case_history`、`ledger`。
- `finish_story()`：普通灵魂走原来的 `release_soul()`；剧情灵魂在 `case_closed` 后按 `result` 放行或拒绝，再统一结算 `payout`。
- 计时：`is_time_suspended()` 增加“剧情面板打开”，避免读台词时来客继续刷。
- 存档：`payload["story"] = {version, world, cases, history, ledger}`；旧存档没有这段时按默认值恢复。
- 面板：复用现有羊皮纸位置和字体；空格推进，数字键或点击选项，F 请他喝药，Shift 结束接待；美术提示（`art`、`speaker`）先接现有立绘，缺图不阻塞。
- 特殊来客默认 `requires_stats = false`：完整灵魂走审查，不走药剂修补；普通灵魂维持现状。这个开关放在案例数据里，不写死在代码里。

## 9. 分期

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| P0 | 装 Godot、搭 `story/` 骨架、夹具案例 | headless 跑通一条路径，测试进 `game/tests/` |
| P1 | 编译器、校验、孙悟空推演与正文入库 | 构建零错误；只改 JSON 就能改剧情 |
| P2 | 对话面板、会话接入、存档、计时 | 游戏里能完整接待孙悟空，读档能续 |
| P3 | 模拟器、重要性矩阵、内容预算、整局结局 | 报告由脚本生成，人能直接审 |

P1 需要先把孙悟空种子里缺的规则补齐：四个破绽的后续动作、叫破身份、接受/拒绝的长期影响、固定 canon、账本、出现时机。这些由 AI 出 `[proposal]`，人改规则，再进编译。
